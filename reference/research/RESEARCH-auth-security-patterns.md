## 1. Multi-Role Authentication in Supabase

### Architecture Overview

Supabase Auth uses **Custom Access Token Hooks** to inject role and tenant information into JWTs before they are issued. This is the foundation for all RBAC in the platform. The chain is:

```
User Login -> Auth Hook fires -> Custom claims injected into JWT -> JWT issued
-> Client sends JWT with requests -> RLS policies read claims -> Access granted/denied
```

### User Types for a Logistics Platform

| User Type    | Auth Method           | Role Storage                    | Notes                              |
|--------------|-----------------------|---------------------------------|------------------------------------|
| Employees    | Email/password, SSO   | `user_roles` table (multi-role) | Multiple roles per employee        |
| Customers    | Email/password, magic link | `app_metadata.user_type = 'customer'` | Linked to `customer_id`     |
| Suppliers    | Email/password, magic link | `app_metadata.user_type = 'supplier'` | Linked to `supplier_id`     |
| Drivers      | Mobile OTP, password  | `app_metadata.user_type = 'driver'`   | Linked to `driver_id`       |
| CEO/Admin    | Email/password + MFA  | `app_metadata.admin = true` + role    | Sees everything, MFA enforced |

### Custom Access Token Hook

This SQL function runs before every token issuance and injects claims:

```sql
CREATE OR REPLACE FUNCTION public.custom_access_token_hook(event JSONB)
RETURNS JSONB
LANGUAGE plpgsql
STABLE
AS $$
DECLARE
  claims JSONB;
  user_roles_arr TEXT[];
  profile RECORD;
BEGIN
  -- Get current claims
  claims := event->'claims';

  -- Fetch user profile
  SELECT * INTO profile
  FROM public.user_profiles
  WHERE user_id = (event->>'user_id')::UUID;

  -- Fetch all roles for this user
  SELECT ARRAY_AGG(role::TEXT) INTO user_roles_arr
  FROM public.user_roles
  WHERE user_id = (event->>'user_id')::UUID;

  -- Inject user_type
  IF profile.user_type IS NOT NULL THEN
    claims := jsonb_set(claims, '{app_metadata, user_type}',
      to_jsonb(profile.user_type));
  END IF;

  -- Inject tenant_id
  IF profile.tenant_id IS NOT NULL THEN
    claims := jsonb_set(claims, '{app_metadata, tenant_id}',
      to_jsonb(profile.tenant_id::TEXT));
  END IF;

  -- Inject roles array
  IF user_roles_arr IS NOT NULL THEN
    claims := jsonb_set(claims, '{app_metadata, roles}',
      to_jsonb(user_roles_arr));
  END IF;

  -- Inject linked entity IDs
  IF profile.customer_id IS NOT NULL THEN
    claims := jsonb_set(claims, '{app_metadata, customer_id}',
      to_jsonb(profile.customer_id::TEXT));
  END IF;

  IF profile.supplier_id IS NOT NULL THEN
    claims := jsonb_set(claims, '{app_metadata, supplier_id}',
      to_jsonb(profile.supplier_id::TEXT));
  END IF;

  IF profile.driver_id IS NOT NULL THEN
    claims := jsonb_set(claims, '{app_metadata, driver_id}',
      to_jsonb(profile.driver_id::TEXT));
  END IF;

  -- Set primary role for the 'role' claim (highest privilege)
  IF 'ceo' = ANY(user_roles_arr) THEN
    claims := jsonb_set(claims, '{user_role}', '"ceo"');
  ELSIF 'admin' = ANY(user_roles_arr) THEN
    claims := jsonb_set(claims, '{user_role}', '"admin"');
  ELSIF user_roles_arr IS NOT NULL AND array_length(user_roles_arr, 1) > 0 THEN
    claims := jsonb_set(claims, '{user_role}', to_jsonb(user_roles_arr[1]));
  END IF;

  event := jsonb_set(event, '{claims}', claims);
  RETURN event;
END;
$$;

-- Security: grant to supabase_auth_admin, revoke from others
GRANT EXECUTE ON FUNCTION public.custom_access_token_hook TO supabase_auth_admin;
REVOKE EXECUTE ON FUNCTION public.custom_access_token_hook FROM authenticated, anon, public;
GRANT ALL ON TABLE public.user_profiles TO supabase_auth_admin;
GRANT ALL ON TABLE public.user_roles TO supabase_auth_admin;
REVOKE ALL ON TABLE public.user_profiles FROM authenticated, anon, public;
REVOKE ALL ON TABLE public.user_roles FROM authenticated, anon, public;
```

After creating this function, enable it in the Supabase Dashboard under **Authentication > Hooks > Custom Access Token Hook**.

## 2. Row Level Security for Complex B2B Apps

### Authorization Helper Function

This function checks if the current user has a specific permission:

```sql
CREATE OR REPLACE FUNCTION public.authorize(requested_permission app_permission)
RETURNS BOOLEAN AS $$
DECLARE
  bind_permissions INT;
  user_roles TEXT[];
BEGIN
  -- Extract roles from JWT (app_metadata.roles)
  SELECT ARRAY(
    SELECT jsonb_array_elements_text(
      (SELECT auth.jwt()->'app_metadata'->'roles')
    )
  ) INTO user_roles;

  -- Check if any of the user's roles have the requested permission
  SELECT COUNT(*) INTO bind_permissions
  FROM public.role_permissions
  WHERE permission = requested_permission
    AND role::TEXT = ANY(user_roles);

  RETURN bind_permissions > 0;
END;
$$ LANGUAGE plpgsql STABLE SECURITY DEFINER;
```

### Performance Optimization (Critical)

Based on Supabase's documented benchmarks, these optimizations yield 94-99% improvements:

```sql
-- 1. ALWAYS add indexes on columns used in RLS policies
CREATE INDEX idx_orders_tenant_id ON public.orders(tenant_id);
CREATE INDEX idx_orders_customer_id ON public.orders(customer_id);
CREATE INDEX idx_orders_created_by ON public.orders(created_by);
CREATE INDEX idx_purchase_orders_tenant_id ON public.purchase_orders(tenant_id);
CREATE INDEX idx_purchase_orders_supplier_id ON public.purchase_orders(supplier_id);
CREATE INDEX idx_deliveries_tenant_id ON public.deliveries(tenant_id);
CREATE INDEX idx_deliveries_driver_id ON public.deliveries(driver_id);
CREATE INDEX idx_deliveries_order_id ON public.deliveries(order_id);
CREATE INDEX idx_invoices_tenant_id ON public.invoices(tenant_id);
CREATE INDEX idx_invoices_customer_id ON public.invoices(customer_id);

-- 2. ALWAYS wrap auth functions in SELECT (prevents re-evaluation per row)
-- GOOD: (SELECT auth.uid())
-- BAD:  auth.uid()

-- 3. ALWAYS specify the TO clause on policies
-- GOOD: FOR SELECT TO authenticated
-- BAD:  FOR SELECT (evaluates for anon too)

-- 4. Use security definer functions for role lookups
-- (already done above with is_admin_user and authorize)

-- 5. ALWAYS add client-side filters that mirror RLS policies
-- Even though RLS will filter, adding .eq('tenant_id', tenantId) to queries
-- dramatically improves performance by allowing index usage before RLS evaluation.
```

## 3. Supabase Auth + Cloudflare Workers

### JWT Verification in Cloudflare Workers

Use the `jose` library for edge-compatible JWT verification against Supabase's JWKS endpoint:

```typescript
// src/middleware/auth.ts
import { jwtVerify, createRemoteJWKSet } from 'jose';

// Supabase JWKS endpoint (uses asymmetric keys)
// Cached automatically by createRemoteJWKSet; additionally cached by
// Supabase Edge for 10 minutes
const JWKS = createRemoteJWKSet(
  new URL('https://<project-ref>.supabase.co/auth/v1/.well-known/jwks.json')
);

interface AuthContext {
  userId: string;
  tenantId: string;
  userType: string;
  roles: string[];
  customerId?: string;
  supplierId?: string;
  driverId?: string;
}

export async function verifyAuth(request: Request, env: Env): Promise<AuthContext> {
  const authHeader = request.headers.get('Authorization');
  if (!authHeader?.startsWith('Bearer ')) {
    throw new Error('Missing or invalid Authorization header');
  }

  const token = authHeader.split(' ')[1];

  try {
    const { payload } = await jwtVerify(token, JWKS, {
      issuer: `https://<project-ref>.supabase.co/auth/v1`,
      audience: 'authenticated',
    });

    const appMetadata = payload.app_metadata as Record<string, any> || {};

    return {
      userId: payload.sub!,
      tenantId: appMetadata.tenant_id,
      userType: appMetadata.user_type,
      roles: appMetadata.roles || [],
      customerId: appMetadata.customer_id,
      supplierId: appMetadata.supplier_id,
      driverId: appMetadata.driver_id,
    };
  } catch (err) {
    throw new Error('Invalid or expired token');
  }
}
```

### JWKS Caching with KV (For High Traffic)

For very high-traffic Workers, cache JWKS keys in Cloudflare KV to avoid cold-start latency:

```typescript
// src/middleware/jwks-cache.ts
import { importJWK, jwtVerify, JWK } from 'jose';

const JWKS_CACHE_KEY = 'supabase_jwks';
const JWKS_CACHE_TTL = 600; // 10 minutes

async function getSigningKey(env: Env): Promise<CryptoKey> {
  // Try KV cache first
  const cached = await env.AUTH_KV.get(JWKS_CACHE_KEY, 'json');
  if (cached) {
    const key = cached.keys[0]; // Use first key
    return importJWK(key as JWK, 'RS256');
  }

  // Fetch from Supabase JWKS endpoint
  const response = await fetch(
    `https://${env.SUPABASE_PROJECT_REF}.supabase.co/auth/v1/.well-known/jwks.json`
  );
  const jwks = await response.json();

  // Cache in KV
  await env.AUTH_KV.put(JWKS_CACHE_KEY, JSON.stringify(jwks), {
    expirationTtl: JWKS_CACHE_TTL,
  });

  return importJWK(jwks.keys[0] as JWK, 'RS256');
}

export async function verifyAuthWithCache(
  request: Request,
  env: Env
): Promise<AuthContext> {
  const token = request.headers.get('Authorization')?.replace('Bearer ', '');
  if (!token) throw new Error('No token');

  const key = await getSigningKey(env);
  const { payload } = await jwtVerify(token, key, {
    issuer: `https://${env.SUPABASE_PROJECT_REF}.supabase.co/auth/v1`,
  });

  // ... extract claims as above
}
```

### Complete Worker with Auth Middleware

```typescript
// src/index.ts
import { verifyAuth, AuthContext } from './middleware/auth';
import { createClient } from '@supabase/supabase-js';

export interface Env {
  SUPABASE_URL: string;
  SUPABASE_KEY: string;            // anon key (respects RLS)
  SUPABASE_SERVICE_ROLE_KEY: string; // service role (bypasses RLS)
  AUTH_KV: KVNamespace;
  MY_RATE_LIMITER: RateLimit;
}

export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    const url = new URL(request.url);

    // Public routes (no auth needed)
    if (url.pathname === '/health') {
      return new Response('OK', { status: 200 });
    }

    // Verify authentication
    let auth: AuthContext;
    try {
      auth = await verifyAuth(request, env);
    } catch (err) {
      return new Response(JSON.stringify({ error: 'Unauthorized' }), {
        status: 401,
        headers: {
          'Content-Type': 'application/json',
          'Cache-Control': 'private, no-store', // Prevent CDN caching auth responses
        },
      });
    }

    // Rate limiting per user
    const { success } = await env.MY_RATE_LIMITER.limit({
      key: auth.userId,
    });
    if (!success) {
      return new Response(JSON.stringify({ error: 'Rate limit exceeded' }), {
        status: 429,
        headers: { 'Content-Type': 'application/json' },
      });
    }

    // Create Supabase client with user's JWT (RLS applies)
    const supabase = createClient(env.SUPABASE_URL, env.SUPABASE_KEY, {
      global: {
        headers: {
          Authorization: request.headers.get('Authorization')!,
        },
      },
    });

    // Route handling
    if (url.pathname.startsWith('/api/orders')) {
      return handleOrders(request, supabase, auth);
    }
    // ... more routes

    return new Response('Not Found', { status: 404 });
  },
};
```

## 4. API Security for Logistics

### Rate Limiting Strategy

```
Layer 1: Cloudflare WAF Rate Limiting Rules
  - Global: 1000 req/min per IP
  - Login endpoint: 10 req/min per IP
  - Password reset: 3 req/min per IP

Layer 2: Cloudflare Workers Rate Limiting Binding
  - Per-user: 100 req/min (standard users)
  - Per-driver: 300 req/min (drivers send frequent location updates)
  - Per-integration: 1000 req/min (API key based)

Layer 3: Application-level
  - Per-endpoint granular limits
  - Expensive operations (reports, exports): 5 req/min
```

Cloudflare Workers rate limiting uses the **key** parameter to identify the rate-limited entity. Use user IDs or API keys rather than IP addresses (many users share IPs on mobile networks).

### API Key Management for Integrations

API key verification in the Worker:

```typescript
async function verifyApiKey(request: Request, env: Env): Promise<ApiKeyContext> {
  const apiKey = request.headers.get('X-API-Key');
  if (!apiKey) throw new Error('Missing API key');

  const keyPrefix = apiKey.substring(0, 8);
  const keyHash = await sha256(apiKey);

  const supabase = createClient(env.SUPABASE_URL, env.SUPABASE_SERVICE_ROLE_KEY);
  const { data, error } = await supabase
    .from('api_keys')
    .select('*')
    .eq('key_hash', keyHash)
    .eq('key_prefix', keyPrefix)
    .is('revoked_at', null)
    .single();

  if (error || !data) throw new Error('Invalid API key');
  if (data.expires_at && new Date(data.expires_at) < new Date()) {
    throw new Error('API key expired');
  }

  // Update last_used_at (fire and forget)
  supabase.from('api_keys').update({ last_used_at: new Date().toISOString() })
    .eq('id', data.id);

  return {
    tenantId: data.tenant_id,
    permissions: data.permissions,
    rateLimit: data.rate_limit,
  };
}
```

### Webhook Security (Outbound)

When your platform sends webhooks to customers/integrations:

```typescript
import { createHmac } from 'node:crypto';

function signWebhookPayload(
  payload: string,
  secret: string,
  timestamp: number
): string {
  const signedContent = `${timestamp}.${payload}`;
  return createHmac('sha256', secret)
    .update(signedContent)
    .digest('hex');
}

async function sendWebhook(url: string, event: object, secret: string) {
  const payload = JSON.stringify(event);
  const timestamp = Math.floor(Date.now() / 1000);
  const signature = signWebhookPayload(payload, secret, timestamp);

  await fetch(url, {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'X-Webhook-Signature': `sha256=${signature}`,
      'X-Webhook-Timestamp': timestamp.toString(),
      'X-Webhook-ID': crypto.randomUUID(),  // Idempotency key
    },
    body: payload,
  });
}
```

### Webhook Security (Inbound)

When receiving webhooks from carriers, payment providers, etc.:

```typescript
async function verifyInboundWebhook(
  request: Request,
  secret: string
): Promise<boolean> {
  const signature = request.headers.get('X-Webhook-Signature');
  const timestamp = request.headers.get('X-Webhook-Timestamp');
  const body = await request.text();

  if (!signature || !timestamp) return false;

  // Replay protection: reject if older than 5 minutes
  const age = Math.floor(Date.now() / 1000) - parseInt(timestamp);
  if (age > 300) return false;

  // HMAC verification
  const expected = createHmac('sha256', secret)
    .update(`${timestamp}.${body}`)
    .digest('hex');

  // Constant-time comparison to prevent timing attacks
  return timingSafeEqual(
    new TextEncoder().encode(`sha256=${expected}`),
    new TextEncoder().encode(signature)
  );
}
```

```typescript
const ALLOWED_TYPES = ['application/pdf', 'image/png', 'image/jpeg',
  'text/csv', 'application/vnd.openxmlformats-officedocument.spreadsheetml.sheet'];
const MAX_FILE_SIZE = 10 * 1024 * 1024; // 10MB

function validateUpload(request: Request): void {
  const contentType = request.headers.get('Content-Type');
  const contentLength = parseInt(request.headers.get('Content-Length') || '0');

  if (!ALLOWED_TYPES.some(t => contentType?.includes(t))) {

  }
  if (contentLength > MAX_FILE_SIZE) {
    throw new Error('File too large');
  }
}
```

## 5. Multi-Tenant vs Single-Tenant for White-Label

### Recommended: Shared Database with Tenant Column + RLS

For a white-label logistics platform on Supabase, the **shared database with tenant_id column** approach is strongly recommended. This is the standard Supabase multi-tenancy pattern.

#### Why Shared Database

| Factor                | Shared DB + tenant_id     | Separate Schemas          | Separate Databases         |
|-----------------------|---------------------------|---------------------------|----------------------------|
| Supabase support      | Native with RLS           | Manual, no tooling        | Requires multiple projects |
| Cost                  | Single project ($25/mo+)  | Single project            | $25/mo per tenant          |
| Complexity            | Low                       | High                      | Very high                  |
| Data isolation         | Strong (RLS enforced)     | Strong (schema boundary)  | Complete                   |
| Cross-tenant queries  | Easy (admin dashboards)   | Complex (search_path)     | Impossible                 |
| Migration/updates     | Single migration          | Per-schema migration      | Per-database migration     |
| Scaling               | Good to ~1000s of tenants | Limited                   | Independent                |

#### Tenant Table

```sql
CREATE TABLE public.tenants (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name TEXT NOT NULL,
  slug TEXT UNIQUE NOT NULL,          -- For subdomain routing: acme.logistics.com
  custom_domain TEXT UNIQUE,          -- Custom domain: logistics.acme.com
  logo_url TEXT,
  primary_color TEXT DEFAULT '#1a1a2e',
  settings JSONB DEFAULT '{}',        -- Tenant-specific config
  plan TEXT DEFAULT 'starter',
  is_active BOOLEAN DEFAULT TRUE,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);
```

#### Every Table Gets tenant_id

```sql
-- Pattern for all business tables

  -- ... business columns ...
```

#### Automatic tenant_id Injection

```sql
-- Trigger to auto-set tenant_id on insert
CREATE OR REPLACE FUNCTION public.set_tenant_id()
RETURNS TRIGGER AS $$
BEGIN
  IF NEW.tenant_id IS NULL THEN
    NEW.tenant_id := (SELECT public.current_tenant_id());
  END IF;

  -- Prevent cross-tenant writes
  IF NEW.tenant_id != (SELECT public.current_tenant_id()) THEN
    RAISE EXCEPTION 'Cannot write to another tenant';
  END IF;

  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- Apply to all business tables
CREATE TRIGGER set_tenant_orders
  BEFORE INSERT ON public.orders
  FOR EACH ROW EXECUTE FUNCTION public.set_tenant_id();

CREATE TRIGGER set_tenant_purchase_orders
  BEFORE INSERT ON public.purchase_orders
  FOR EACH ROW EXECUTE FUNCTION public.set_tenant_id();

-- ... repeat for all tables
```

#### White-Label Domain Routing

In Cloudflare Workers, resolve tenant from subdomain or custom domain:

```typescript
async function resolveTenant(request: Request, env: Env): Promise<string> {
  const host = request.headers.get('Host') || '';

  // Check custom domain first
  const supabase = createClient(env.SUPABASE_URL, env.SUPABASE_SERVICE_ROLE_KEY);

  // Try custom domain
  let { data: tenant } = await supabase
    .from('tenants')
    .select('id')
    .eq('custom_domain', host)
    .eq('is_active', true)
    .single();

  if (tenant) return tenant.id;

  // Try subdomain
  const slug = host.split('.')[0]; // e.g., "acme" from "acme.logistics.com"
  ({ data: tenant } = await supabase
    .from('tenants')
    .select('id')
    .eq('slug', slug)
    .eq('is_active', true)
    .single());

  if (tenant) return tenant.id;

  throw new Error('Tenant not found');
}
```

For custom domains, use Cloudflare for SaaS (SSL for SaaS) to handle SSL certificates automatically for tenant custom domains.

### Audit Trail Implementation

Use Supabase's `supa_audit` extension for comprehensive change tracking:

```sql
-- Enable the audit extension
CREATE EXTENSION IF NOT EXISTS supa_audit CASCADE;

-- Enable tracking on all business tables
SELECT audit.enable_tracking('public.orders'::regclass);
SELECT audit.enable_tracking('public.purchase_orders'::regclass);
SELECT audit.enable_tracking('public.deliveries'::regclass);
SELECT audit.enable_tracking('public.invoices'::regclass);
SELECT audit.enable_tracking('public.inventory'::regclass);
SELECT audit.enable_tracking('public.customers'::regclass);
SELECT audit.enable_tracking('public.suppliers'::regclass);
SELECT audit.enable_tracking('public.user_roles'::regclass);
SELECT audit.enable_tracking('public.api_keys'::regclass);
```

This creates triggers that automatically log all INSERT, UPDATE, and DELETE operations to `audit.record_version` with:
- Full record snapshot (JSONB)
- Previous record snapshot (for updates/deletes)
- Timestamp
- Operation type
- Stable `record_id` derived from primary key

Query audit history:

```sql
-- View all changes to a specific order
SELECT op, ts, record, old_record
FROM audit.record_version
WHERE table_name = 'orders'
  AND record->>'id' = 'order-uuid-here'
ORDER BY ts DESC;

-- View all changes by a specific user in the last 24 hours
SELECT table_name, op, ts, record
FROM audit.record_version
WHERE record->>'updated_by' = 'user-uuid-here'
  AND ts > NOW() - INTERVAL '24 hours'
ORDER BY ts DESC;
```

### Data Retention Policies

```sql
-- Automated cleanup of old audit data (run via pg_cron)
-- Keep detailed audit records for 2 years, summary for 7 years

-- Install pg_cron extension
CREATE EXTENSION IF NOT EXISTS pg_cron;

-- Archive old audit records monthly
SELECT cron.schedule(
  'archive-audit-records',
  '0 2 1 * *',  -- 2 AM on the 1st of every month
  $$
    -- Move records older than 2 years to archive
    INSERT INTO audit.record_version_archive
    SELECT * FROM audit.record_version
    WHERE ts < NOW() - INTERVAL '2 years';

    DELETE FROM audit.record_version
    WHERE ts < NOW() - INTERVAL '2 years';
  $$
);

-- Clean up activity logs older than 7 years
SELECT cron.schedule(
  'cleanup-activity-logs',
  '0 3 1 * *',
  $$
    DELETE FROM public.activity_log
    WHERE created_at < NOW() - INTERVAL '7 years';
  $$
);
```

### GDPR-Specific Considerations

```sql
-- Function to handle "right to erasure" requests
CREATE OR REPLACE FUNCTION public.gdpr_erase_user(target_user_id UUID)
RETURNS VOID AS $$
BEGIN
  -- Anonymize orders (keep for financial records but remove PII)
  UPDATE public.orders
  SET customer_notes = NULL
  WHERE created_by = target_user_id;

  -- Delete user profile
  DELETE FROM public.user_profiles WHERE user_id = target_user_id;

  -- Delete the auth user (cascades to user_roles, etc.)
  -- This must be done via supabase.auth.admin.deleteUser() from application code

  -- Log the erasure request itself
  INSERT INTO public.activity_log (tenant_id, action, entity_type, entity_id, metadata)
  VALUES (
    (SELECT tenant_id FROM public.user_profiles WHERE user_id = target_user_id),
    'gdpr.erasure_completed',
    'user',
    target_user_id,
    jsonb_build_object('erased_at', NOW())
  );
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;
```

## Summary: Architecture Decision Record

### Stack

| Component | Technology | Purpose |
|-----------|-----------|---------|
| Auth      | Supabase Auth + Custom Access Token Hook | JWT-based auth with custom claims |
| Authorization | PostgreSQL RLS + permission tables | Row-level data isolation |
| API Gateway | Cloudflare Workers | JWT verification, rate limiting, routing |
| Database  | Supabase (PostgreSQL) | Shared database, tenant_id isolation |
| File Storage | Supabase Storage (private buckets) | Tenant-scoped file access |
| Rate Limiting | Cloudflare Workers Rate Limiting binding | Per-user, per-tier limits |
| CDN/WAF   | Cloudflare | DDoS protection, WAF rules, SSL |
| Audit     | supa_audit extension + custom activity_log | Compliance and debugging |
| Cron Jobs | pg_cron | Data retention, cleanup |

### Key Principles

1. **Database-level security**: RLS policies are the last line of defense; never rely solely on application logic.
2. **JWT claims for performance**: Inject roles and tenant_id into JWT to avoid per-request database lookups for authorization.
3. **Shared database for multi-tenancy**: Every table has `tenant_id`; every RLS policy checks it.
4. **Edge verification**: Validate JWTs in Cloudflare Workers before requests reach Supabase.
5. **Defense in depth**: Cloudflare WAF -> Worker rate limiting -> JWT verification -> RLS policies.
6. **Audit everything**: supa_audit for data changes, auth.audit_log_entries for auth events, activity_log for business events.
