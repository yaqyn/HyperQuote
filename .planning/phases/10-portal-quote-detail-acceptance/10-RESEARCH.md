# Phase 10: Portal Quote Detail + Acceptance - Research

**Researched:** 2026-04-01
**Domain:** Portal UI (quote detail, negotiation flows, server-side quote actions)
**Confidence:** HIGH

## Summary

Phase 10 builds the quote detail view inside the portal's Orders window. When a customer receives a quote (status "sent"), they see a rich detail page with timeline, line items with prices, VAT breakdown, and validity countdown. Four actions are available: Accept (creates order + proforma invoice via DB trigger), Counter-Offer (total discount or per-line price editing), Partial Accept (per-line accept/reject/negotiate), and Decline (with optional reason).

The heavy lifting is split between: (1) a new dynamic route `orders_.$quoteId.tsx` for the quote detail page, (2) four server functions (`acceptQuote`, `submitCounterOffer`, `submitPartialResponse`, `rejectQuote`) following the established `createServerFn` + `.inputValidator()` + `.handler()` pattern, and (3) ~15 new UI components specified in the UI-SPEC. The `on_quote_accepted()` trigger is a database concern -- the UI just calls `acceptQuote()` and the trigger handles order + PO + proforma invoice creation.

**Primary recommendation:** Build server functions first (with dev-mode fallback), then the route with loader, then components top-down (QuoteDetail > QuoteHeader > QuoteTimeline > LineItemsTable > SubtotalsSection > ActionBar > Modals > Counter/Partial flows > VersionHistory/Comparison).

### Anti-Patterns to Avoid
- **Using `watch()` instead of `useWatch()`:** RHF `watch()` is broken with React 19. Use `useWatch()` for the counter-offer form.
- **Putting editing state in React state:** Cross-component communication (LineItemsTable <-> FloatingChangesBar) needs shared state. Use Zustand.
- **Animating color changes:** Per UI-VISION, color changes (amber highlight) are instant. No transition/animation on background color.
- **Client-side order creation logic:** The `on_quote_accepted()` trigger lives in the database. The UI calls `acceptQuote()` which updates quote status; the trigger handles everything else.

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Currency formatting | Custom number formatter | `CurrencyDisplay` from @hyperquote/ui | Handles AR locale, Arabic-Indic numerals, EGP prefix/suffix |

## Common Pitfalls

### Pitfall 1: RLS Policy Restricts Customer Quote Access
**What goes wrong:** Customer can only see quotes with status IN ('sent', 'accepted', 'rejected', 'expired'). Queries for 'negotiating' or 'revised' quotes return empty.
**Why it happens:** RLS policy `quotes_customer_select` restricts visible statuses.
**How to avoid:** The UI must handle the case where a counter-offer was submitted (status changed to 'negotiating') and the quote is still visible because the RLS allows 'sent' -> customer updates to 'accepted'/'rejected' only. Check: when counter-offer is submitted, does the status change server-side and remain visible? The RLS may need to include 'negotiating' and 'revised' for customer SELECT.
**Warning signs:** Quote disappears from customer view after submitting counter-offer.

### Pitfall 2: Stale Quote Status Race Condition
**What goes wrong:** Customer views quote (status 'sent'), but by the time they click Accept, the quote has expired or been revised.
**Why it happens:** No real-time status sync; quote data loaded once in route loader.
**How to avoid:** Re-fetch quote status in the `acceptQuote` server function before processing. Return appropriate error if status changed. Consider `staleTime: 60_000` and `refetchOnWindowFocus: true` on the quote query.
**Warning signs:** Accept succeeds on expired quote; confetti shows but order isn't created.

### Pitfall 3: Counter-Offer Creates New Version, Old Version Becomes Uneditable
**What goes wrong:** After submitting counter-offer, the original quote status changes to 'negotiating'. The customer expects to see the new version but gets confused.
**Why it happens:** Counter-offer creates a NEW quote row with incremented `version_number` and `previous_version_id` pointing to the original.
**How to avoid:** After counter-offer submission, redirect to the new version's quote ID. The version history section shows the chain via `previous_version_id`.
**Warning signs:** Customer sees old version after submitting counter-offer.

### Pitfall 4: RTL Layout for Number Alignment
**What goes wrong:** Prices and totals appear left-aligned in Arabic mode.
**Why it happens:** Using `text-right` instead of logical properties.
**How to avoid:** Use `text-end` (logical property) for all number columns. React Aria Table handles column alignment correctly with RTL.
**Warning signs:** Numbers shift sides when switching between AR and EN.

### Pitfall 5: Hydration Mismatch with Validity Countdown
**What goes wrong:** Server renders "5 days remaining" but client computes "4 days remaining" due to timezone differences.
**Why it happens:** Date math during SSR uses server time; client uses local time.
**How to avoid:** Compute days remaining on the server (in the loader) and pass as a number. Client only decrements via interval. Or use `ClientOnly` for the countdown component.
**Warning signs:** React hydration error on quote detail page.

### Pitfall 6: Multiple Rapid Clicks on Accept
**What goes wrong:** Multiple orders created for the same quote.
**Why it happens:** No optimistic UI lock or idempotency.
**How to avoid:** Disable the Accept button immediately on press (`isDisabled={mutation.isPending}`). Server function should check quote status is still 'sent' before processing.
**Warning signs:** Duplicate orders in the database.

## Code Examples

### Server Function Pattern (from existing codebase)
```typescript
// Source: apps/portal/src/lib/server/quote-requests.ts (line 79-197)
export const acceptQuote = createServerFn()
  .inputValidator(z.object({ quoteId: z.string().uuid() }))
  .handler(async ({ data: input }): Promise<{ orderId: string; status: string }> => {
    if (!isSupabaseConfigured()) {
      return { orderId: crypto.randomUUID(), status: 'confirmed' }
    }

    const session = await getServerSession({
      supabaseUrl: process.env.SUPABASE_URL!,
      supabaseAnonKey: process.env.SUPABASE_ANON_KEY!,
    })
    if (!session) throw new Error('Unauthorized')

    const { createClient } = await import('@supabase/supabase-js')
    const supabase = createClient(
      process.env.SUPABASE_URL!,
      process.env.SUPABASE_ANON_KEY!,
      {
        global: {
          headers: { Authorization: `Bearer ${session.session.access_token}` },
        },
      },
    )

    // Update quote status -- triggers on_quote_accepted()
    const { data, error } = await supabase
      .from('quotes')
      .update({ status: 'accepted', accepted_at: new Date().toISOString() })
      .eq('id', input.quoteId)
      .eq('status', 'sent')  // Guard: only accept if still 'sent'
      .select('id')
      .single()

    if (error || !data) {
      throw new Error(error?.message ?? 'Quote is no longer available for acceptance')
    }

    // The on_quote_accepted() trigger creates the order
    // Fetch the created order ID
    const { data: order } = await supabase
      .from('orders')
      .select('id')
      .eq('quote_id', input.quoteId)
      .single()

    return {
      orderId: order?.id ?? '',
      status: 'confirmed',
    }
  })
```

## Open Questions

1. **RLS visibility of 'negotiating' quotes**
   - What we know: RLS policy restricts customer SELECT to status IN ('sent', 'accepted', 'rejected', 'expired')
   - What's unclear: After counter-offer (status -> 'negotiating'), can the customer still see the quote?
   - Recommendation: Server function should handle this -- either the RLS needs updating (Phase 13 DB work), or the counter-offer flow keeps the quote visible by not changing status until internal review. For now, dev mode mocks bypass RLS. Flag for Phase 13.

2. **Confetti implementation specifics**
   - What we know: Blue + white particles, 300ms, Motion v12
   - What's unclear: Exact particle count, spread, gravity simulation
   - Recommendation: Simple approach -- 20-30 absolute-positioned divs animated with Motion `animate` and staggered delays. Not worth a library for a 300ms effect.
